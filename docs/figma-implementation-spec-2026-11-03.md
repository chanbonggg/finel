# Figma 디자인 적용 상세 계획 명세서

작성일: 2026-11-03

검토·보완일: 2026-11-05

상태: **백엔드·프론트 구현 반영 / 운영 경로 검증 대기**. 실제 API 계약은 `docs/api-contract.md` 0절이 기준이다. 2절은 구현 착수 전의 기준 상태다.

착수 방침(2026-11-05): **프론트는 수정하지 않고 백엔드부터 구현한다.** 문의 읽음 API → 상품 확장 → PDF 업로드·상품 연결 → 백엔드 회귀 검증 순서로 진행한다. 화면 연결·시각 검증은 후속 프론트 단계이며, 백엔드 완료와 전체 기능 완료를 구분한다. 이번 문서 수정은 착수 순서와 범위를 정리하는 작업이며 실제 DB 적용·배포를 승인하지 않는다.

백엔드 구현 기록(2026-11-05): 문의 읽음 PATCH, 선택 규격·모델명·용도·상세 규격, PDF 분할 업로드·공개 조회·상품별 시작 페이지를 구현했다. V2 SQL은 격리 PostgreSQL 16에서 새 DB 초기화와 V1 업그레이드, JPA 검증, JSONB 저장과 공유 참조를 확인했다. 로컬 Docker/Nginx에서는 1,000,000,000바이트 합성 PDF 전송·검증, 1바이트 초과 거부, 컨테이너 교체 후 조회, DB와 파일 볼륨을 함께 복원한 뒤 조회를 확인했다. 실제 Cloudflare 경로와 운영 파일 검증은 남아 있다.

프론트 구현 기록(2026-11-05): Figma 메인 `60:5231`, 공개 목록·상세·문의 `60:5366`·`60:5602`·`60:5702`, 회사 소개·개인정보처리방침 `21:2`·`23:2`, 카테고리 `49:2`, 관리자 `70:1976`·`70:2152`·`70:2295`·`70:2449`를 확인했다. 공용 헤더는 밝은 2단 구성으로 통일했다. 제품 비교는 최대 3개이며 제품군이 달라도 선택할 수 있다. 관리자 등록·수정은 기존 URL 안에서 화면을 전환한다. 회사 소개의 기존 지도와 개인정보처리방침 본문을 사용한다.

프론트 검증 기록: `npm run lint`, `npm run build`와 격리 PostgreSQL/Spring에 연결한 Edge 테스트를 통과했다. 자동완성·목록 URL 복원·비교 상한, 제품 선택 문의 및 일반 문의, 관리자 로그인, 불완전한 규격 입력 거부, 손상 PDF 거부, PDF 취소·전송·Range·저장·해제, 문의 상세의 읽음 저장을 검증했다. 360·768·1440px에서 공개·관리자 주요 경로의 가로 넘침을 확인했다. 실제 Cloudinary 이미지 업로드와 운영 Cloudflare 경로는 이 검증에 포함되지 않았다.

검토 결론: 기존 공개·인증·문의 접수 흐름을 보존하면서 상품 데이터 확장과 PDF 등 필요한 계약 변경을 함께 진행한다. 기존 Figma 기록에 선택형 브랜드·처리 상태·접수 상품 스냅샷이 있지만, 현재 구현 범위는 아래 운영 결정을 우선한다. **독립 브랜드·상품 스냅샷 확장은 도입하지 않고 처리 상태는 보류한다. 상품 확장·서버 저장 PDF(파일당 최대 1GB)·자동 읽음·일반 문의를 구현 대상으로 한다.** 기존 필드만 사용하는 화면 변경 단계는 이 확정 범위 전체의 완료가 아니다.

## 0. 확정한 운영 기준 (2026-11-05)

| 항목 | 확정한 동작 | 구현 영향·남은 확인 |
|---|---|---|
| 브랜드 | 브랜드 없는 상품은 없다. 기존 회사별 제품군 관계를 유지한다. | 브랜드는 `category.companyId`에서 파생한다. 독립 `brandId` 컬럼·브랜드 없음 옵션·브랜드 이관은 도입하지 않는다. |
| 상품 필수 입력 | 제품명·제품군만 필수. 모델명·규격·용도·설명·이미지·PDF는 선택이다. 상세 규격은 항목/값 행으로 입력한다. | `spec` 필수 검증을 변경한다. 길이·최대 행 수 등 수치는 기존 데이터 확인 후 구현 설계에서 정한다. |
| PDF | 서버 디스크에 파일당 최대 1GB로 저장한다. 누구나 열 수 있고 여러 상품이 같은 카탈로그를 공유하며 상품마다 시작 페이지를 지정한다. | 1GB는 1,000,000,000바이트로 정의한다. 영구 볼륨·분할 업로드·공개 다운로드와 페이지 검증을 설계한다. 기존 이미지 Cloudinary 업로드는 유지한다. |
| 문의 읽음 | 관리자에서 문의 상세를 열면 읽음 처리한다. | 기존 `isRead` 컬럼을 사용한다. 처리 상태와 수동 안 읽음 복원은 이번 단계에 추가하지 않는다. |
| 문의 메일 | 문의 내용을 메일로 수신하는 요구를 유지한다. 사용자가 오류를 의심하지만 원인은 미확인이다. | 오류 조사·수정과 실제 수신 검증은 후속 작업이다. 현재 저장 후 비동기 발송 경계를 보존한다. |
| 일반 문의 | 상품을 선택하지 않은 문의도 접수한다. | 제품 선택은 선택 입력이다. 일반 문의에는 상품 요약·상품 상세 복귀 링크를 만들지 않는다. |
| 상품 스냅샷 | 신규 스냅샷을 도입하지 않는다. 기존 문의의 제품명 문자열 저장만 유지한다. | 과거 모델·제품군·규격·PDF를 복사하지 않는다. 문의에 상품 ID/FK를 추가하는 설계도 이번 단계에서 제외한다. |

원시안과 달라지는 독립 브랜드·처리 상태·상품 스냅샷 항목은 디자인 대조 시 이 결정에 맞춰 정리한다. 기존 제품명 문자열과 문의 원문은 보존하되 과거 상품 정보 전체를 제공한다고 표현하지 않는다.

## 1. 목표와 범위

Figma의 공개 화면과 관리자 화면을 현재 Next.js·Spring Boot 애플리케이션에 연결한다. 제품 탐색 → 상세 확인 → 문의 접수와 관리자 상품·문의 관리를 실제 데이터로 동작시키고, 기존 공개·인증·문의 접수 계약을 보존한다.

- 디자인 기준 후보: Figma 파일 `3Lxpu1pxuwnchCr5kCyxg8`, 페이지 `02 · 전체 화면 (목데이터)` 및 `04 · 카테고리 템플릿`. 예시 제품과 문의는 실제 데이터가 아니다.
- 대상: 공통 헤더/푸터, 홈, 제품 목록·비교, 제품 상세, 카테고리, 문의, 회사 소개, 개인정보처리방침, 관리자 상품 목록·등록·수정·문의 목록. 관리자 로그인은 별도 시안 여부 확인.
- 제외: 실제 DB 변경 및 migration 실행, 배포, 운영 데이터 수정, 새 데이터 수집, 지도 업체 선정. 기능 추가와 스키마는 아래 결정 후 별도 구현한다.
- 현재 구현 범위: 백엔드 API·검증·영속성·테스트와 관련 계약 문서. 프론트 화면·타입·API 클라이언트는 이번 단계에서 수정하지 않는다. PDF에 필요한 저장소·프록시 설정안은 PDF 단계에서 함께 준비하되 실제 운영 반영은 별도 절차로 둔다.
- 우선순위: P0 기존 프론트 요청·응답 호환과 문의 읽음 API, P1 상품 확장, P2 PDF 업로드·상품 연결 및 백엔드 회귀 검증. 일반 문의는 기존 백엔드의 상품 미선택 허용 동작을 검증한다. 공개/관리자 화면 적용은 백엔드 이후 진행한다. 독립 브랜드·상품 스냅샷 확장은 제외하고 처리 상태·메일 오류 조사는 후속 작업으로 분리한다. 완료 보고는 백엔드 완료·프론트 연결·전체 기능 완료를 구분한다.

## 2. 확인한 현재 상태

| 항목 | 현재 구현에서 확인한 사실 | 영향 |
|---|---|---|
| Product | `id`, `name`, `categoryId`, `spec`, `description`, `imageUrl`, `isVisible`, 생성·수정 시각. `spec`은 문자열 하나다. | 이름·제품군·등록된 규격의 비교는 DB 변경 없이 가능하다. 세부 규격별 필터는 구조화 데이터가 없어 보장할 수 없다. |
| Category | 이름과 `companyId`를 갖고 이름·회사 조합이 유일하다. | 같은 이름의 서로 다른 카테고리는 ID로 구분한다. 전체 목록 API는 `companyId`가 필수다. |
| Inquiry | 이름·연락처·이메일·내용·회사·제품명 문자열·`isRead`·생성 시각. | 상품 ID, 문의 제목, 상품 규격 스냅샷, 처리 상태는 현재 응답에 없다. 기존 상품명으로 특정 상품을 신뢰성 있게 역추적할 수 없다. |
| 공개 검색 | `GET /api/products/search?q=`는 공개 제품의 이름 부분 일치, 최신순 최대 10개. 빈 질의는 빈 배열. | 현재 API는 자동완성에 적합하며 모델·용도 검색과 전체 검색 결과는 보장하지 않는다. |
| 목록 선택 상태 | `ProductsClient`는 category ID로 옵션을 모으지만 선택·필터 비교는 `product.category` 이름으로 한다. 브랜드·제품군·페이지는 컴포넌트 메모리에만 있다. | ID 선택으로 전환하는 것은 신규 수정 사항이다. URL 복원과 동명 카테고리 구분을 별도로 구현·검증한다. |
| 공개 제품 | 목록·상세·검색에서 숨김 제외. 상세의 숨김 상품은 404. | 비교나 링크에서도 숨김 상품을 드러내지 않는다. |
| 문의 | 공개 POST, 관리자 GET·DELETE. 저장 commit 후 메일 비동기 예약; 메일 실패는 접수 성공을 되돌리지 않는다. | UI 변경 중 검증·중복 방지·오류 분기와 저장/메일 경계를 유지한다. |
| 문의 상태 | `isRead` 컬럼은 있지만 변경 API는 없다. 처리 상태 필드도 없다. | 읽음 변경에는 백엔드 변경, 처리 상태 영구 저장에는 추가 저장 공간과 백엔드 변경이 필요하다. |
| 관리자 | `/chanyoung` 탭 기반. 상품 CRUD, 이미지 업로드, 카테고리 관리, 문의 조회·삭제가 있다. | 시안에 없는 기존 삭제·카테고리 관리·로그아웃의 위치를 보존하거나 명시 결정한다. |
| 브랜드 | `ProductResponse.companyId`는 `Product.category.companyId`에서 파생되고 브랜드 이름·로고는 프론트 `PARTNERS` 상수로 표시한다. V1에는 Company/Brand 테이블이 없다. | 이 관계를 그대로 유지한다. 브랜드 없는 상품·독립 브랜드는 구현 범위에서 제외하며 가짜 회사 ID를 만들지 않는다. |
| 업로드 | `POST /api/uploads/images`만 존재한다. JPEG/PNG/WebP/GIF, 5 MiB 제한이며 PDF endpoint와 상품 PDF 필드는 없다. | PDF 업로드·페이지 연결은 신규 기능이다. 이미지 endpoint를 그대로 PDF에 연결할 수 없다. |
| 관리자 공개 여부 | PATCH는 `isVisible`을 지원하지만 현재 상품 폼 상태와 저장 payload에는 해당 조작이 없다. 상품 생성은 항상 공개 기본값이다. | API 지원과 실제 화면 지원을 구분한다. 기존 숨김 값을 수정 과정에서 의도치 않게 바꾸지 않는다. |
| 공통 layout | 루트 `app/layout.tsx`가 모든 경로에 Navbar/Footer를 렌더링하며 `app/chanyoung/layout.tsx`는 children을 반환한다. | 관리자 사이드바 시안을 적용하려면 공개/관리자 shell 분리가 필요하다. |
| DB 운영 | JPA는 `ddl-auto=validate`, Flyway migration은 append-only. 현재 저장소에는 V1 baseline이 있다. | 실제 DB의 상태와 Flyway 이력은 별도로 확인해야 하며, 코드만으로 운영 DB 상태를 단정하지 않는다. |

## 3. 화면 및 동작 명세

### 3.1 공통 내비게이션

- 로고 → `/`; 회사 소개 → `/about`; 오시는 길 → `/about`의 해당 위치; 문의 → `/contact`; 전체 제품 → `/products`. 현재 오시는 길은 `/about` 링크이므로 앵커는 실제 대상 요소 추가 시에만 사용한다.
- 상단 검색 입력은 기존 검색 API 및 300ms debounce, 실패·빈 결과 표시를 활용한다. 결과 선택 시 `/products/{id}`. 엔터/검색 버튼이 전체 결과로 가는지 자동완성 첫 결과를 선택하는지는 결정 필요; 기본 제안은 검색어가 유지되는 제품 목록이다. 이 경우 10개 제한 자동완성 API를 전체 결과로 오인하지 않도록 별도 결과 조회 방식을 결정한다.
- 제품군은 실제 category ID를 이용해 이동한다. 카테고리 표시의 출처와 노출 순서, 제품이 없는 카테고리 노출 여부는 결정 필요. 현재 무인자 category API는 사용할 수 없다.
- 모바일에서 메뉴·검색을 키보드와 터치로 조작하고 포커스·열림 상태를 제공한다. 시안에 없는 모바일 배치는 별도 확정한다.

### 3.2 홈

- 검색, 제품군 선택, 전체 제품 보기, 실제 추천 제품 상세, 문의 및 전화 링크를 제공한다. 대표 제품은 기존 featured API의 공개 데이터만 사용한다.
- 데이터 없음과 API 오류를 구분해 안내한다. 시안의 가짜 상품명·규격·빈 이미지를 실제 상품으로 하드코딩하지 않는다.

### 3.3 제품 목록 및 비교

- 기존 브랜드·제품군 선택, 제품 상세 이동, 페이지 이동과 비어 있음 상태를 보존한다. 카테고리는 이름이 아닌 ID로 선택한다.
- 비교 제안: 동일 화면에서 제품 선택/해제, 비교 표 표시, 전체 해제; 첫 버전은 페이지 안의 메모리 상태로만 유지한다. 선택 상한과 다른 제품군 간 비교 가능 여부는 미확정이다.
- 비교 필드는 실제 응답에 존재하는 제품명·브랜드·제품군·`spec`만 표시하고, 미입력은 '정보 없음'으로 구분한다. `spec`을 항목별로 임의 분해하지 않는다.
- Figma는 카드가 아닌 선택 체크박스가 있는 목록 표와 하단 비교표를 보여 준다. 전체 적용 시 표 구조, 등록 규격 문자열 필터, '필터 적용'·'초기화', 제품명 정렬, 카테고리별 개수와 결과 개수를 구현한다. 예시의 9개·2개 선택을 상수로 쓰지 않는다. 상세 규격 수치 범위 필터는 시안에서 확인된 요구가 아니다.
- 모델명·용도는 시안에서 별도 행이며 예시 값이 '미등록'이다. 실제 필드가 추가되기 전에는 미등록으로 표시하고, 상품 확장 이후 해당 필드를 연결한다.
- 필터 변경·페이지 이동 시 선택 유지 여부, 필터 밖 선택 표시, 새로고침과 숨김·삭제된 제품 처리 규칙을 확정한다. 공개 데이터로만 비교하므로 기본 구현에 신규 DB/API는 불필요하다.
- 목록은 현재 공개 제품을 한 번에 읽어 브라우저에서 필터·페이지 처리한다. 대량 데이터에서 서버 페이지네이션이 필요할지는 실제 규모와 성능 확인 후 별도 결정한다.

### 3.4 제품 상세와 카테고리

- 상세는 이미지, 이름, 제품군, 저장된 `spec`과 설명을 표시한다. 이미지가 없으면 대체 상태를 제공한다. 문의 버튼은 기존 `/contact?product=...`, 전화 버튼은 `tel:` 연결을 유지한다.
- 시안의 '제품 정보'·'설명 · 용도'는 해당 섹션으로 이동하는 앵커로 구현하는 방안을 우선한다. '제품군의 다른 제품 보기'는 category ID 경로로 이동한다. '카탈로그 PDF 보기'는 저장된 문서와 페이지가 유효할 때만 활성화한다(10.3절).
- 카테고리는 실제 ID 기반 조회, 해당 공개 제품만 표시, 전체 목록으로 이동. 잘못된 ID·미존재 항목은 404, 제품 없는 카테고리는 빈 상태를 유지한다.
- 공개 상세·카테고리의 metadata, canonical, sitemap, 구조화 데이터 및 캐시 무효화 동작은 회귀 확인한다.

### 3.5 문의

- 이름·연락처·문의 내용·개인정보 동의는 필수이고 이메일·제품 선택은 선택이다. 제품 목록 로딩 실패가 일반 문의 제출을 막지 않게 한다. 제출 중 상태와 400/429/서버 오류를 표시한다.
- 제출은 기존 공개 API를 호출하고 중복 제출을 막는다. 성공은 DB 접수 완료를 뜻하며 메일 발송 성공으로 표현하지 않는다. 실패 시 사용자의 입력을 보존한다.
- 일반 문의를 허용한다. 상품을 고르지 않으면 서버에 가짜 상품명 '일반 문의'를 저장하지 않고 상품 연결 없이 접수한다. UI에는 '일반 문의 (제품 선택 안 함)' 옵션을 제공한다. 기존 `기타` 선택은 호환하되 자유 상품명 전용 입력란은 별도 요구가 생기기 전 추가하지 않고 문의 내용에 적도록 안내한다.
- 문의 메일 수신은 운영 요구다. 사용자가 발송/수신 오류를 의심하고 있으나 이번 작업에서 증상·원인을 확인하지 않았다. 후속 조사로 남기며 메일 수신 정상화 완료를 선언하지 않는다.
- 시안의 선택 상품 요약·'제품 변경'·'제품 상세로 돌아가기'·개인정보 '내용 보기'를 연결한다. 제품 변경은 선택 입력으로 포커스를 이동하는 방안을 우선하고, 개인정보 링크는 `/privacy`로 연결한다. 상품 ID가 없는 자유 입력/기타 문의에는 상세 복귀 링크를 만들지 않는다(10.4절).

### 3.6 회사 소개·개인정보처리방침

- 제품 목록·문의·파트너 링크의 실제 목적지를 유지한다. 지도는 시안에서 자리표시이므로 지도 제공 방식 및 주소 검증 전에는 임의의 지도를 확정하지 않는다.
- 개인정보 처리방침의 사실관계·운영 주체·처리 항목·보관 정책은 별도 확인한다. 시안 문구를 현재 운영 사실이나 법적 검토 결과로 간주하지 않는다.

### 3.7 관리자 상품 관리

- 사이드바에서 상품·문의 전환, 사이트 보기, 로그아웃을 제공한다. 기존 인증 guard와 API 인증/CSRF를 유지한다.
- 목록의 수정·삭제, 등록 진입, 새로고침, 기존 카테고리 추가·삭제를 유지한다. 삭제는 현재 hard delete이며 확인 절차와 오류 응답을 유지한다.
- 등록·수정의 필수값은 제품명·카테고리다. 설명·이미지·규격 등은 선택이며 공개 여부 계약을 보존한다. 저장 중 중복 제출을 방지하고 실패 시 입력을 유지한다. 회사 선택은 해당 회사의 제품군을 고르는 기존 단계이며 독립 브랜드 저장값이 아니다.
- **확정된 계약 변경:** 현재 백엔드는 `name/spec`의 blank를 거부하지만 목표는 규격 선택 입력이다. 프론트·백엔드·계약·테스트를 함께 바꾸고 비어 있는 `spec`은 빈 문자열로 저장해 기존 NOT NULL을 유지하는 방안을 우선한다. 실제 변경 전 현재 API가 빈 규격을 허용한다고 간주하지 않는다.
- 등록·수정의 모델명·규격 행·용도·PDF와 페이지 입력은 10절의 상품 확장 범위다. 브랜드는 기존 회사/제품군 관계로 표시한다. 이미지 드래그 안내는 있으나 현재 코드에는 drop handler가 없으므로 실제 drop 동작도 구현 대상으로 기록한다. 저장 요청 중 상태는 현재 훅에 없으므로 새로 보강한다.
- 별도 경로로 분리할지 기존 탭 상태로 구성할지는 결정 사항이다. URL을 바꾸면 직접 접근, 새로고침, guard 및 복귀 경로를 함께 검증한다.

### 3.8 관리자 문의 관리

- 기존 목록을 선택 가능한 목록·상세로 구성한다. 검색은 현재 내려받은 관리자 목록에서 이름·회사·제품명·내용을 대상으로 수행하는 방안을 우선한다. 개인정보를 URL, 로그 또는 분석 이벤트에 넣지 않는다.
- 현재 응답으로 표시할 수 있는 값: 이름·회사·연락처·이메일·제품명·본문·접수 시각·읽음 여부. 문의 제목을 임의 생성하지 않으며 상품 상세 스냅샷·처리 상태는 이번 구현에서 제외한다. '문의 접수 당시 제품 정보' 대신 저장된 문의 제품명을 표시하고 상품명으로 현재 상품 상세 링크를 추측하지 않는다.
- 문의 제목 입력은 공개 문의 시안에도 없다. 새 제목 컬럼을 필수로 추가하지 않고, 목록은 제품명과 본문 첫 줄 요약을 구분해 표시하는 방안을 권장한다. 원문을 바꾸거나 시안의 예시 제목을 복사하지 않는다. 날짜는 UTC 응답을 화면에서 `Asia/Seoul`로 일관되게 표시하는 방안을 제안한다.
- 이메일이 있을 때만 `mailto:` 등 외부 메일 앱 연결을 제안한다. 이는 메일 앱 실행이며 사이트에서 답장 발송이나 발송 성공을 보장하지 않는다. 이메일 없음은 비활성화·안내한다. 기존 문의 삭제 동작도 보존한다.
- 문의 상세를 열면 자동 읽음 처리한다. 읽음 저장 실패 시 기존 서버 상태를 유지하고 사용자에게 알리며 재시도를 제공한다. 처리 상태와 수동 안 읽음 복원 UI는 이번 단계에서 제외한다.

## 4. 데이터·백엔드 변경 후보

### 4.1 읽음 상태 — DB 컬럼 재사용, API 추가 필요

- 확정: 관리자 문의 상세가 표시되면 해당 문의를 읽음으로 저장한다. 목록을 불러오거나 메일을 발송한 것만으로 읽음 처리하지 않는다. 수동 안 읽음 복원은 이번 단계의 요구가 아니다. 자동 처리 실패 시 실패 안내와 재시도를 제공한다.
- 제안 API: `PATCH /api/inquiries/{id}/read` 본문 `{ "isRead": true }`. 이번 단계는 읽음 설정만 지원한다. 성공 시 갱신된 상태를 포함한 응답, 미존재 404, 잘못된 본문 400, 인증 없음 401, CSRF 실패 403. 기존 오류 형식과 일치시킨다.
- 백엔드: Inquiry 도메인 메서드·서비스 트랜잭션·DTO·컨트롤러·테스트를 추가한다. 기존 `isRead` 컬럼을 사용하므로 이 기능만을 위한 신규 컬럼은 필요 없다. 보안 규칙은 11절의 실제 fallback을 유지하고 불필요한 matcher를 추가하지 않는다.
- 같은 값 재요청은 같은 상태로 끝나도록 한다. 읽음 PATCH가 처리 상태 등 다른 필드를 덮어쓰지 않도록 갱신 대상을 제한한다. 동시 실행 시 '마지막 응답 수신'을 '마지막 저장'으로 간주하지 않으며, 프론트는 문의 ID·필드별 쓰기를 직렬화하거나 요청 중 조작을 막아 역전 응답을 방지한다. 다중 관리자 충돌 감지가 필요하면 버전 검증을 별도 설계한다.

### 4.2 처리 상태 — 이번 단계 보류

현재 요구는 상세 열람 시 읽음 처리까지다. 아래 처리 상태 설계는 후속 후보로 남기며 `handlingStatus` 컬럼·상태 API·필터/선택기·기존 문의 상태 초기화를 이번 단계에 포함하지 않는다. 문의 메일 오류 조사도 별도 후속 작업이다.

- 시안의 표시 값은 '신규', '확인 중', '처리 완료'다. API 값 제안은 `NEW`, `IN_PROGRESS`, `DONE`이다. 실제 업무 의미·허용 전이·초기값은 운영자 결정 후 확정한다. 읽음 여부와 처리 상태는 별개다.
- 결정 후 `Inquiry`에 새 상태 필드를 추가하는 방안을 우선 검토한다. DB 기본값/nullable 여부, 체크 제약과 기존 행 변환은 실제 데이터와 배포 순서를 확인한 다음 설계한다. 기존 문의를 모두 `NEW`로 표시하면 실제 처리 이력과 다를 수 있으므로 임의 일괄 분류하지 않는다.
- 제안 API: `PATCH /api/inquiries/{id}/status`, 허용된 값만 검증하고 관리자 인증·CSRF를 적용한다. 응답·401/403/404/400 및 실패 시 UI 복구를 계약에 명시한다.
- 최소 저장안 제안: nullable 문자열 `handlingStatus`, 신규 접수는 `NEW`, 기존 행의 null은 화면에서 '기존 문의 · 상태 미확인'. 허용된 세 값 또는 null만 저장하도록 제약을 둔다. 과거 문의에 실제 완료 여부를 추측해 채우지 않는다. 전체 필터는 미확인 행도 포함한다. 이는 제안이며 실제 초기화 정책 확정 후 migration을 작성한다.
- 서버/DB 변경 전에는 필터·선택기를 실제 기능처럼 내보내지 않는다. 작업자·변경 이력·댓글은 요구 확인 전 추가하지 않는다.

### 4.3 문의와 제품 연결 — 스냅샷 확장 제외 확정

- 기존 `Inquiry.product` 문자열을 유지한다. 신규 상품 ID/FK·제품군·모델명·규격 스냅샷 필드와 과거 데이터 backfill을 추가하지 않는다.
- 일반 문의는 상품명 없이 접수하고 상품 선택 문의는 기존 상품명 alias 계약으로 접수한다. 상품 삭제·이름 변경 후에도 기존 문의의 문자열과 원문을 보존한다.
- 동명·변경·삭제된 상품을 이름으로 자동 매칭하지 않는다. 관리자 문의에는 저장된 상품명만 표시하고 특정 상품 링크나 과거 규격을 보장하지 않는다. 공개 문의 화면의 일시적인 ID 선택·복귀 링크와 DB의 상품 참조 저장은 구분한다(10.4절).

### 4.4 검색과 규격 — 단계적 선택

- 1단계: 기존 name 검색과 현재 문자열 `spec` 표시. UI가 실제 지원하지 않는 모델·용도 검색을 약속하지 않는다.
- 2단계 후보: `spec` 또는 `description` 검색이 운영 데이터에서 의미가 있는지 확인한 뒤 검색 계약을 확장한다. 기존 자동완성의 10개 제한과 새로운 전체 결과의 계약을 명확히 분리하거나 변경 영향 전체를 검토한다. 검색어 길이 제한, 빈 값, 공개 여부, 정렬, 페이징과 인덱스는 데이터량·실행 계획 확인 후 결정한다.
- 3단계 후보: 규격별 정렬·범위 필터가 실제로 필요하면 필드 정의·단위·결측값·입력과 기존 데이터 정제 계획을 먼저 정한다. 기존 자유 텍스트를 자동으로 구조화된 사실로 간주하지 않는다.
- 전체 시안에는 별도 모델명·용도와 상세 규격 입력이 있으므로 10.1절에서 데이터 구조를 제안한다. 문자열 `spec`의 부분 일치 필터와 상세 규격 행 저장은 서로 다른 기능이며, 세부 규격별 검색 인덱스·수치 범위 필터는 이번 요구로 간주하지 않는다.

## 6. migration 및 배포 계획 — 실행 전 별도 승인

1. 변경이 필요한 기능과 스키마를 확정하고, 실제 대상 DB의 스키마·Flyway 이력·배포 구조 및 백업 복구 가능성을 확인한다. 현 문서만으로 운영 상태를 추정하지 않는다.
2. 기존 스키마를 보존하는 신규 버전 SQL을 작성하고 빈 PostgreSQL과 기존 스키마/대표 테스트 데이터를 이용한 격리 환경에서 검증한다. 운영 데이터를 테스트에 복제할 때는 별도 정책과 승인에 따른다.
3. `ddl-auto=validate`를 유지하고 migration 이후 JPA 매핑 검증, 이전·신규 API 호환과 기존 행 보존을 확인한다. `flyway clean`, baseline, 기존 migration 수정은 사용하지 않는다.
4. 기존 서버와 새 스키마, 새 서버와 기존 클라이언트의 호환성을 확인해 배포 순서를 정한다. 기존 DB의 Flyway 활성화·baseline은 실제 이력에 따라 별도 절차를 수립한다. 복구는 백업 복원과 서비스 중단 범위를 포함해 사전에 연습한다.
5. 운영 DB 적용 및 배포는 구체적인 변경안과 대상 확인 후 별도 명시 승인으로 진행한다. 적용 전후 검증과 문제가 생겼을 때 중단 기준을 준비한다.

## 7. 검증 및 완료 기준

- 공개 흐름: 홈 → 검색/카테고리 → 목록/비교 → 상세 → 제품 선택된 문의 → 접수; 키보드·모바일·빈 결과·이미지 없음·API 오류를 확인한다.
- 공개 경계: 숨김 상품은 검색·목록·상세·비교·metadata/sitemap에 노출되지 않는다. 없는 제품/카테고리는 기존 404 정책을 유지한다.
- 관리자 상품: 로그인 만료, 목록·등록·수정·삭제, 업로드 실패, 카테고리 충돌/삭제 실패, 공개 여부 변경과 캐시 갱신을 확인한다.
- 관리자 문의: 목록·검색·선택·삭제, 이메일 없음, 상세 열람 시 읽음 저장 성공·실패·재시도, 반복 열람과 401/403/404를 확인한다. 처리 상태는 이번 완료 조건에서 제외한다.
- 문의 접수: 상품 미선택 일반 문의와 상품 선택 문의 모두에서 필수 검증·개인정보 동의·중복 제출·400/429/DB 실패를 확인한다. 저장 성공 후 메일 실패에도 접수를 유지하고 민감정보를 노출하지 않는다. 실제 메일 오류 조사·수신 검증은 보류다.
- 스키마 변경 시 빈 PostgreSQL migration/JPA validate와 기존 행 유지·선택된 삭제 정책을 테스트한다. 실제 DB·SMTP·Cloudinary 검증은 별도 승인과 안전한 환경에서만 수행한다.
- 상품 신규 필드의 생성·수정·초기화, 카테고리에서 파생한 브랜드, 규격 미입력·행 추가/삭제/정렬, PDF 공유·상품별 페이지·교체·연결 해제, 예전 클라이언트 수정 시 새 필드 보존을 검증한다. 문의 스냅샷 확장은 검증 범위에서 제외하고 기존 문의 제품명 보존을 확인한다. 전체 검증 항목은 13절에 둔다.
- 현재 백엔드 단계는 `./gradlew.bat test`와 관련 API·보안·DB 검증을 수행한다. API 변경 시 `docs/api-contract.md`를 갱신하고 기존 프론트 요청 fixture로 호환성을 확인한다. 프론트 소비 코드 확장과 `npm run lint`, `npm run build`, 시안·실제 렌더링 비교는 후속 프론트 단계에서 수행한다. 아래 화면 검증 항목과 17절 시나리오는 백엔드 테스트만으로 통과 처리하지 않는다.

## 8. 확정 사항과 남은 결정

1. 밝은 2단 헤더를 카테고리·개인정보 화면에도 공통 적용할지, 모바일 시안을 어떻게 정할지.
2. 검색 버튼의 목적지와 검색 대상(제품명, `spec`, 용도), 전체 결과·자동완성 범위.
3. 비교 최대 개수, 교차 제품군 비교, 선택 유지 범위와 비교 항목.
4. **확정:** 상세 열람 시 자동 읽음. 처리 상태·수동 안 읽음 복원은 이번 단계 제외. 문의 메일 오류 조사는 후속 작업.
5. **확정:** 문의 스냅샷 확장과 DB 상품 ID 연결 제외. 기존 상품명 문자열을 보존하며 이름으로 특정 상품 링크를 추측하지 않는다.
6. 관리자 상품 등록·수정의 별도 URL 여부, 기존 카테고리 관리·문의 삭제·로그아웃 배치.
7. 지도 방식, 실제 회사/개인정보 문구, 로고 자산의 최종 선택.
8. **확정:** 기존 회사별 카테고리와 브랜드 관계 유지. 상품은 제품명·제품군만 필수이고 나머지 입력은 선택. 이미지는 현재 1장 구조를 기본으로 유지하며 다중 이미지는 별도 요구 시 검토.
9. **확정:** 서버 디스크·파일당 최대 1GB·공개 PDF·카탈로그 공유·상품별 시작 페이지. 남은 기술 설계는 영구 볼륨 경로·권한·분할 업로드·페이지 검증·백업/복구. 연결 해제와 파일 물리 삭제는 구분.
10. **확정:** 일반 문의 허용·상품 스냅샷 확장 제외. 기존 문의 상품명 alias와 이전 클라이언트 호환을 유지한다.

## 9. 확정 작업 순서 — 백엔드 우선

각 단계에서 관련 구현·가장 가까운 작업 지침·현재 API 계약을 확인하고 코드·테스트·계약 문서를 함께 갱신한다. 문서 전체의 미결정을 먼저 해소할 필요는 없으며, 해당 기능에 필요한 입력 제한·API·자원 한도는 그 단계의 구현 전에 확정한다. 프론트를 변경해야만 동작하는 기존 계약의 파괴적 변경은 이번 단계에서 도입하지 않는다.

| 단계 | 구현 범위 | 백엔드 완료 기준 |
|---|---|---|
| 1. 문의 읽음 API | `PATCH /api/inquiries/{id}/read`, 기존 `isRead` 재사용. 누락/null/false 거부, true 반복 호출 허용. | 서비스·HTTP 계약·인증/CSRF·404·반복 호출 테스트. DB 스키마 변경 없음. 문의 도메인 작업 지침의 기존 읽음 API 제외 문구도 새 계약에 맞춰 갱신. |
| 2. 상품 확장 | `spec` 선택 입력, `modelName`, `useCase`, 순서 있는 `specifications`. 기존 브랜드 파생 관계 유지. | 길이·최대 행 수·중복 항목명 정책을 계약에 고정. 생성·수정·초기화·기존 행 보존·legacy PATCH의 신규 필드 보존 검증. 필요한 신규 migration은 6절의 별도 스키마 작업·승인 절차를 따름. |
| 3. PDF 업로드·상품 연결 | 분할 업로드 → 파일 검증·저장 → 공개 다운로드 → 상품별 시작 페이지 연결 순서. | 정확한 API·오류·조각 크기·만료/정리·동시 업로드·파싱 자원 한도 확정. 공유·연결 해제·Range·보안·실패 정리 검증 및 저장소/프록시 설정안·운영 문서 준비. |
| 4. 백엔드 회귀 검증 | 일반 문의와 기존 상품·문의·공개 조회·관리자 흐름의 서버 계약 확인. | 상품 미선택 및 기존 alias, 숨김 상품 비노출/404, 기존 상품 수정, 저장 commit 후 비동기 메일 경계 검증. `./gradlew.bat test` 결과와 PostgreSQL 테스트 실행/skip을 구분해 기록. |

- **기존 프론트 호환:** 응답 envelope·기존 필드·상태 코드·alias를 유지하고 새 선택 필드를 추가한다. 기존 프론트가 새 필드를 보내지 않아도 상품 수정 시 저장된 값이 유지되어야 한다. 11.2절의 누락·null·빈 배열 의미를 계약과 테스트로 고정한다. 새 프론트 타입·호출은 후속 단계에서 추가한다.
- **일반 문의:** 현재 백엔드는 상품명 없는 요청을 허용한다. 이 동작과 기존 메일/저장 경계를 우선 검증하며, 새 상품 ID/FK·스냅샷을 추가하지 않는다. 상품 선택을 선택 입력으로 바꾸는 화면 작업은 후속 프론트 범위다.
- **PDF 완료 구분:** 단위·API·파일 테스트 통과와 실제 환경 검증을 따로 기록한다. 실제 1GB 전송·메모리/디스크/시간 측정·컨테이너 교체 후 보존·백업 복구가 미검증이면 PDF 전체 완료로 보고하지 않는다. 운영 DB 적용·배포는 6절에 따라 별도 승인 후 수행한다.
- **후속 프론트 단계:** 공통 shell·홈·목록·상세·문의·관리자 화면에 새 API를 연결한다. 상세 열람 시 읽음 호출, 상품 신규 입력·PDF 분할 전송, 일반 문의 UI와 실패 복구를 구현하고 lint/build·브라우저·접근성·반응형·시각 검증을 수행한다. 백엔드 API 추가만으로 자동 읽음이나 화면 기능이 완성되었다고 표현하지 않는다.
- **후속 별도 작업:** 처리 상태·메일 오류 조사 및 실제 수신 검증. 독립 브랜드·문의 상품 스냅샷 확장은 구현 대상에서 제외한다.

실제 운영 DB 내용, 실제 트래픽 규모, 모바일 렌더링 및 외부 서비스는 검증하지 않았다. Figma 확인 기록의 범위와 이번 보완의 확인 범위는 2절을 따른다.

## 10. 누락 기능 보완: 상품 데이터·파일·문의 연결 상세안

### 10.1 상품 필드와 상세 규격

아래는 **구현 후보 구조**이며 현재 DB 컬럼이 아니다. 실제 SQL은 결정사항 확정 및 별도 스키마 작업에서 작성한다. 기존 Product의 필드·ID·관계와 NOT NULL 제약은 필요한 변경 외에는 보존한다.

운영 기준은 제품명·제품군만 필수로 확정했다. 기존 `spec`과 새 모델명·용도·상세 규격·PDF는 미입력을 허용한다. 아래 표는 이를 구현할 저장 형태의 후보이며 길이·행 수 등 제한값은 구현 전에 확정한다.

| 후보 필드 | 형태와 미입력 | 동작·검증 | 기존 데이터 처리 |
|---|---|---|---|
| `modelName` | nullable 문자열 | 상품 모델명. 공백만 있으면 null. 규격 문자열과 별개로 표시·검색한다. | null로 시작. `spec`에서 추측해 채우지 않는다. |
| `useCase` | nullable TEXT | 관리자가 확인한 용도. 일반 텍스트로 표시한다. | null. 설명에서 자동 추출하지 않는다. |
| `specifications` | JSONB 배열, 기본 `[]` | `[{"name":"항목명","value":"값"}]` 형태. 배열 순서를 표시 순서로 쓰고 추가·삭제를 지원한다. | 빈 배열. 기존 `spec`은 요약 규격으로 보존한다. |
| `catalogFileId`, `catalogPage` | nullable 정수 쌍 | 10.3절의 문서 및 시작 페이지 참조. 둘 다 없음 또는 유효한 조합만 허용한다. | 둘 다 null. |

- 상세 규격은 표시와 편집만 요구되므로 처음부터 규격 사전·단위 변환·규격별 인덱스·수치 검색을 만들지 않는다. JSONB 배열 타입은 DB 제약으로, 각 원소의 필수 name/value와 개수·길이 제한은 요청 경계에서 검증한다. 지원하지 않는 값은 조용히 버리지 않고 400을 반환한다.
- UI의 새 빈 규격 행은 아직 저장할 데이터가 아니다. 양쪽이 빈 행은 저장 전에 제외하고 한쪽만 입력한 행은 필드 오류를 표시한다. 저장된 데이터에는 반쪽 행을 허용하지 않는다. 중복 항목명 허용 여부, 최대 행 수·필드 길이는 구현 전에 계약에 수치로 고정한다.
- 현재는 이미지 URL 하나만 저장한다. 1장만 사용할 경우 업로드한 이미지를 대표 이미지로 간주하고 '대표 이미지 지정'은 그 상태를 표현한다. 다중 이미지와 대표 선택을 원한다면 별도 데이터 모델과 UI 요구가 생기므로 단일 이미지 기능에 숨겨 추가하지 않는다.
- 공개 목록·상세·비교, 관리자 목록·폼, Product DTO, 메타데이터와 테스트 fixture가 새 필드의 소비자다. 용도와 설명은 서로 덮어쓰지 않는다. `spec`이 모델명으로 사용되는 기존 구조화 데이터도 확인하고, 새 모델명이 없을 때 사실과 다른 model 값을 만들지 않는다.

### 10.2 브랜드와 카테고리 — 기존 관계 유지 확정

브랜드 없는 상품은 취급하지 않는다. 기존 회사별 카테고리를 유지하고 상품의 브랜드는 `Product.category.companyId`에서 파생한다.

- Product에 독립 `brandId`를 추가하지 않는다. 브랜드 없음 옵션·브랜드 관리 테이블·기존 상품 브랜드 이관도 도입하지 않는다. 이름·로고는 현재 `PARTNERS` 매핑을 재사용한다.
- 관리자 폼에서 회사 선택은 제품군 목록을 좁히는 기존 단계다. 제품군 선택 시 브랜드가 결정되며 서로 다른 독립 브랜드를 함께 저장하지 않는다. 회사 변경으로 선택 제품군이 유효하지 않게 되면 재선택을 요구한다.
- 공개 목록의 브랜드 필터는 기존 `companyId`를 사용한다. 같은 이름의 다른 회사 카테고리는 ID로 구분하며 합치지 않는다. 선택 옵션에는 회사 문맥을 표시한다.
- 기존 시안 기록의 '브랜드 선택 안 함'은 채택하지 않는다. 디자인 대조 시 회사/제품군에 따른 브랜드 표시로 맞춘다.

### 10.3 PDF 업로드·연결·교체·연결 해제

- 확정: PDF는 서버 디스크에 보관하고 파일당 최대 **1GB(1,000,000,000바이트)**를 허용한다. 로그인 없이 누구나 열 수 있고 여러 상품이 하나의 카탈로그를 공유한다. 문서 ID는 공유하되 시작 페이지는 상품별로 저장한다. 같은 PDF를 상품 A는 3쪽, 상품 B는 10쪽으로 연결할 수 있다. 기존 이미지 업로드는 Cloudinary와 5 MiB 제한을 유지한다.
- 저장소의 `docker-compose.yml`은 Cloudflare Tunnel → Nginx → Spring 구성이며 백엔드 파일 영구 볼륨이 아직 없다. `nginx/conf.d/finel.tunnel.conf`는 `client_max_body_size 10m`다. 이는 저장소 구성 확인 결과이며 운영 서버의 실제 설정·디스크 여유·요금제는 확인하지 않았다.
- Cloudflare는 요금제별 HTTP 요청 본문 제한을 둔다. 파일 전체 한도와 한 요청의 한도를 구분하고 현재 경로에서는 **분할 업로드**로 1GB를 지원한다. Nginx 제한만 1GB로 높이면 해결된다고 가정하지 않는다. [Cloudflare 요청 크기 제한](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/4xx-client-error/error-413/).
- 분할 업로드 최소안은 서버 발급 임시 업로드 ID → 순차 조각 전송 → 완료 검증이다. 조각은 우선 8 MiB 이하로 잡아 현재 10m 요청 한도 내에 둔다. 서버는 실제 누적 크기·선언한 전체 크기·조각 순서·중복·완료 상태를 검증한다. UI는 진행률을 표시한다. 관리자 인증·CSRF를 모든 업로드 단계에 적용하고 업로드를 만든 관리자와 연결한다. 중단·만료된 임시 파일은 정리한다. 새로고침·서버 재시작 후 자동 재개는 초기 범위에 추가하지 않고 새 업로드를 시작한다.
- 파일을 byte 배열·base64로 통째로 만들지 않는다. 브라우저는 파일을 잘라 전송하고 서버는 디스크로 기록·검증한다. 기존 이미지 업로드의 `file.getBytes()` 처리를 PDF에 복사하지 않는다. multipart·프록시 제한은 조각과 전송 부가정보를 수용하도록 맞추고 파일 전체 1GB 한도는 서버가 별도로 강제한다. 완료 시 파일 기반 PDF 파싱의 임시 공간·메모리·실행 시간도 제한하고 실측한다.
- 영구 저장 경로는 소스·컨테이너 이미지·일회성 컨테이너 계층과 분리한다. PDF용 Docker 영구 볼륨 또는 호스트 디렉터리를 백엔드에 마운트하고 기존 non-root 사용자 `finel`의 쓰기 권한을 맞춘다. 실제 경로는 배포 환경에 맞춰 설정한다. 임시/확정 파일은 구분하고 백업에 DB metadata와 실제 PDF를 함께 포함해 복구를 검증한다. 영구 볼륨은 재배포 시 보존 수단이며 디스크 장애에 대한 백업을 대신하지 않는다.
- 저장명은 서버가 발급하고 원본 파일명을 디스크 경로로 사용하지 않는다. 경로 이탈·동명 덮어쓰기를 막고 임시/검증 실패 파일은 공개하지 않는다. 잔여 디스크·임시 복사본·동시 업로드 한도를 확인해 공간이 없으면 기존 파일을 건드리지 않고 실패를 반환한다. 1GB는 파일별 한도이며 서버 전체 보관량 한도가 아니다.
- 보관 metadata 후보는 `CatalogFile`의 문서 ID·내부 저장 키·파일 크기·페이지 수·UTC 생성 시각이다. Product는 문서 ID·시작 페이지를 참조한다. 관리자 폼은 상품에 이미 연결된 문서 metadata를 ID로 모아 기존 카탈로그 선택을 제공한다. 전체 파일 라이브러리·내용 해시 기반 중복 제거는 초기 요구에 추가하지 않는다.
- 서버는 크기·실제 PDF 형식·읽기 가능 여부·페이지 수를 검증한다. 비어 있거나 손상된 파일·암호 때문에 검증할 수 없는 PDF는 거부한다. 전체 파일 저장·검증이 끝난 뒤에만 `{ success: true, catalog: { id, pageCount } }`를 반환한다. 검증·metadata 저장 실패 시 미완료 파일이 정상 문서로 남지 않게 정리한다. 파일시스템과 DB를 하나의 원자적 transaction으로 가정하지 않는다.
- 공개 파일 조회는 문서 ID로 확정 파일만 찾아 `application/pdf`로 제공한다. 임의 경로·업로드 임시 파일·서버 절대 경로를 공개하지 않는다. 큰 파일의 Range 요청·206·잘못된 범위의 416과 전체 파일 응답의 Content-Length를 검증한다. 페이지 이동은 실제 PDF 페이지 순서를 사용하고 뷰어의 fragment 동작을 확인한다. 해당 공개 GET 경로만 SecurityConfig에 허용하고 업로드 POST를 공개하지 않는다.
- 상품 저장 시 `catalogFileId`, `catalogPage`를 받고 문서 존재와 `1 <= page <= pageCount`를 검증한다. 업로드·교체는 저장 성공 전까지 폼의 임시 변경이다. 새 파일은 새 문서로 등록해 공유 중인 기존 파일을 덮어쓰지 않는다. 한 상품의 연결 해제·페이지 변경이 다른 상품에 영향을 주지 않게 한다. 공개 PDF이므로 상품을 숨겨도 이미 알려진 파일 주소를 회수하지 않는다.
- 파일 물리 삭제는 공유 참조·편집·취소 업로드를 고려하는 별도 정리 절차로 둔다. 초기에는 상품 삭제와 함께 PDF를 자동 삭제하지 않는다. 취소·저장 실패로 남는 확정 파일의 확인·정리 방법을 운영 문서에 기록한다.

### 10.4 문의의 선택 상품 — 기존 상품명 저장 유지

- 상품 미선택 일반 문의를 허용하고 상품명은 비워 접수한다. 기존 `productName`/`product` alias와 저장 commit 후 메일 비동기 예약을 유지한다. 신규 서버 상품 ID 요청·FK·스냅샷 컬럼은 추가하지 않는다.
- 공개 문의 화면은 `/contact?productId={id}`를 화면 선택용으로 사용할 수 있다. 실제 공개 제품을 확인한 경우에만 요약·복귀 링크를 만들고 제출에는 기존 상품명을 사용한다. 같은 이름의 상품을 화면에서 구분하려면 ID로 선택하되 이 ID를 문의 DB에 보관한다고 약속하지 않는다. 기존 `?product=` 이름 링크도 받는다.
- 화면용 ID가 404/숨김/삭제 상태이면 상품 재선택 또는 일반 문의 전환을 제공하고 다른 상품을 이름으로 추측하지 않는다. 일반 문의·기타·이름만 있는 legacy 링크에는 확정된 상세 복귀 링크를 만들지 않는다.
- 관리자 문의는 저장된 제품명과 원문을 표시한다. '접수 당시 규격/제품군' 영역은 도입하지 않는다. 상품 변경·삭제 후에도 문의의 제품명과 원문을 그대로 읽을 수 있으며 특정 상품을 영구 식별하거나 과거 규격을 재현하는 기능은 제공하지 않는다.

## 11. API 확장·호환·보안의 구체 기준

### 11.1 제안 endpoint와 응답

| 호출 | 변경 여부 | 요청·결과 기준 |
|---|---|---|
| `GET /api/products`, `/{id}`, `/featured`, `/search` | 기존 응답 확장 | 기존 envelope·필드·visibility 유지. 새 상품 필드는 미등록을 null/빈 배열로 명시한다. |
| `POST/PATCH /api/products[/{id}]` | 기존 요청 확장 | 모델·용도·선택 규격·규격 행·PDF 참조. 브랜드는 카테고리에서 파생한다. POST 201, PATCH 200 및 기존 Product 응답을 유지한다. |
| `POST /api/uploads/catalogs` 및 조각/완료/취소 하위 경로 | 신규 분할 업로드 후보 | 관리자·CSRF 필요. 시작 시 임시 ID를 발급하고 조각은 8 MiB 이하, 합계는 최대 1GB로 검증한다. 완료 검증 후 문서 metadata 반환. 정확한 하위 경로·본문·오류는 구현 시 계약에 확정한다. |
| `GET /api/catalogs/{id}/file` | 신규 공개 조회 후보 | 확정된 문서만 PDF로 전달한다. Range·206·416을 지원하고 없는 파일은 404다. 디스크 경로·임시 파일은 노출하지 않는다. |
| `GET /api/inquiries` | 기존 응답 재사용 | 기존 `isRead`와 상품명 문자열로 표시한다. 별도 상세 endpoint·상품 스냅샷 응답 확장은 추가하지 않는다. |
| `PATCH /api/inquiries/{id}/read` | 신규 설계 후보·동작 확정 | `{ "isRead": true }` → 200 `{ success: true, message, inquiry }`. 누락/null/false는 이번 읽음 전용 요청에서 허용하지 않는다. |
| `PATCH /api/inquiries/{id}/status` | 보류·이번 구현 제외 | 4.2절의 후속 후보다. 현재 API처럼 호출하거나 상태 컬럼을 추가하지 않는다. |
| `POST /api/inquiries` | 기존 요청 호환 | 제품 미선택을 허용한다. 기존 상품명 alias·201·오류 stage·메일 비동기 정책을 유지하고 상품 ID·스냅샷 요청 필드는 추가하지 않는다. |

위 응답은 계약 초안이다. 백엔드 구현 시 `docs/api-contract.md`와 서버 테스트를 함께 확정하고 기존 프론트와의 호환을 유지한다. frontend 타입·호출·실패 분기의 확장은 후속 프론트 단계에서 갱신한다. 상태 변경에는 문의 등록 전용 `stage`를 불필요하게 도입하지 않는다.

### 11.2 PATCH와 이전 클라이언트

- 현재 Product PATCH는 name/spec 등의 값을 다시 받는 폼 저장 방식이며 일반적인 모든 필드 부분 수정 API가 아니다. 규격 선택 입력 변경 시 `spec`의 빈 문자열 허용과 누락 처리 범위를 계약에 명시한다. 기존 필드 전체를 임의로 생략해도 된다고 해석하지 않는다.
- 새 선택 필드는 **누락=기존 값 보존**, **명시적 null=선택값 해제**, **값 제공=대체** 규칙을 권장한다. 규격 행은 `[]`로 전체 해제한다. POST의 누락은 미등록 기본값을 사용한다.
- 단순 Java record의 nullable 필드만으로 누락과 null을 구분할 수 있다고 가정하지 않는다. 요청 필드 존재를 구분할 수 있는 프로젝트에 맞는 최소 DTO 처리가 필요하다. 프론트 API 타입도 `undefined` 생략과 `null` 해제를 표현한다. 이전 화면에서 수정했다고 새 PDF·모델 정보가 지워지는 회귀를 막는다.
- 숨김 상품의 관리자 수정은 현재 `includeHidden=true` 목록에서 값을 가져온다. 수정 화면을 별도 URL로 만들 때 공개 `GET /products/{id}`로 불러오면 숨김 상품은 404다. 최소 구현은 인증된 전체 목록을 재사용하며, 필요성이 확인될 때만 관리자 상세 API를 추가한다.

### 11.3 보안 경계와 데이터 노출

- 현재 SecurityConfig는 지정 공개 경로 외 `anyRequest().authenticated()`다. 신규 PATCH와 모든 분할 업로드 단계는 이 fallback으로 보호한다. 공개 PDF 다운로드를 위한 GET 경로만 정확히 허용하고 `/api/uploads/**` 전체를 공개하지 않는다. 필요하면 공개 PDF GET의 쿠키 토큰 해석도 기존 공개 조회 정책에 맞춘다. CSRF 예외는 `/api/inquiries` 기본 경로이며 하위 PATCH·업로드를 예외로 확대하지 않는다.
- 테스트는 인증 없는 요청에 유효한 CSRF를 붙여 401을 확인하고, 인증된 요청에 CSRF가 없으면 403/`CSRF_INVALID`를 확인한다. 인증과 CSRF가 둘 다 없을 때 항상 401이라고 단정하지 않는다.
- 관리자 쓰기는 `authenticatedFetch`를 사용한다. 403 이후 토큰 캐시를 비우는 기존 동작을 재사용하고 요청을 임의 자동 재전송하지 않는다. 404이면 삭제된 대상과 선택 상태를 갱신한다.
- 현재 관리자 문의/상품 전체 조회는 `no-store`다. 고객 정보와 상태를 public cache·localStorage에 저장하지 않는다. 문의 본문·규격·파일명은 일반 텍스트로 표시하고 HTML로 실행하지 않는다. 외부 링크는 검증된 HTTPS URL을 사용하고 새 탭에 안전한 rel 속성을 둔다.
- 고객 문의 버튼 잠금은 연속 클릭 방지이며 서버 중복 접수 방지 키와 같지 않다. 네트워크가 끊겨 성공 여부를 모르면 자동 재접수하지 않고 불확실한 상태를 안내한다. 별도 idempotency 저장소는 이 문서만으로 추가하지 않는다.

## 12. 프론트 구조·상태·이동의 수용 기준

- 관리자 shell 분리 제안: 최상위 layout은 공통 html/body·폰트·metadata를 소유하고 공개 헤더/푸터는 공개 route group layout으로 옮긴다. 관리자 layout은 sidebar/header를 소유한다. URL `/`, `/products/**`, `/contact`, `/chanyoung/**`는 보존하고 로그인에도 공개/관리자 메뉴가 중복되지 않게 한다. 메인 영역의 의미와 관리자 noindex도 유지한다.
- 명시된 검색 버튼·엔터는 `/products?q=...`로 이동하는 방안을 권장한다. 첫 결과로 자동 이동하지 않는다. 기존 전체 공개 목록에서 이름 검색을 처리하면 별도 전체 결과 API 없이 10개를 넘는 검색 결과를 표시할 수 있다. 상품 확장 후 modelName/useCase를 같은 조건에 연결한다. 자동완성 API의 최대 10개와 목록 결과를 구분한다.
- 기존 `translateSearchQuery`는 한글 키워드를 영어로 바꾼다. 새 검색창·목록의 정책을 통일하고 원문 한국어 상품명과 변환 별칭 모두를 놓치지 않도록 fixture로 확인한다. 검색어의 화면 표시를 영어로 강제 치환하지 않는다. 대소문자·앞뒤 공백·0건·10건 초과도 확인한다.
- 제품 목록 필터는 초안/적용 상태를 구분한다. '필터 적용'에서 브랜드·규격 문자열 조건을 반영하고 페이지를 1로 되돌린다. '초기화' 범위는 검색어까지 포함하는지 확정한다. 전체 브랜드·전체 카테고리로 돌아갈 수 있어야 한다. 제품명 정렬은 같을 때 ID로 순서를 고정하는 방안을 제안한다.
- 비교 기본안 제안: 2개 이상일 때 비교 이동을 활성화하고 최대 3개, 교차 카테고리 비교 허용. 필터·페이지 이동 시 ID 선택은 유지하고 상세로 나가거나 새로고침하면 해제한다. 0/1개·상한 초과·선택 제거·필터 밖 선택 개수를 안내한다. 시안이 상한을 정한 것은 아니므로 이 값은 구현 전 확정한다.
- 비교 선택은 최신 재조회 결과에서 숨김·삭제된 ID를 제거한다. 서버 공개 API의 hidden 제외는 유지하지만 이미 브라우저에 전달된 값이나 최대 300초 캐시를 즉시 회수할 수 있다고 약속하지 않는다. mutation 뒤 기존 AFTER_COMMIT revalidation이 동작하는지와 실패 시 남는 캐시 시간을 확인한다.
- 문의 목록 선택은 ID로 유지한다. 선택 문의 삭제·필터로 제외·읽음 변경 후 필터에서 사라짐·재조회 중 선택 소실의 다음 선택 규칙을 정한다. '안 읽음' 필터에서 열어 읽음으로 바꾼 문의는 본문 확인을 끝낼 수 있도록 선택 상세를 유지한다. 반복 렌더링·동일 문의 재선택으로 불필요한 읽음 요청을 반복하지 않는다.
- 관리자 편집의 '취소'·'목록으로'는 변경사항을 버리기 전 확인하고 저장하지 않은 upload 교체가 원본 연결을 바꾸지 않게 한다. '변경사항 없음'은 데이터 비교로 산출한다. 저장/업로드 중에는 충돌하는 조작을 막고 완료 후 목록과 선택 상태를 응답 데이터로 갱신한다.
- 접근성 확인에는 label-input 연결, 검색 결과 키보드 이동·선택·ESC, 비교 체크박스의 상품별 이름, 테이블 헤더, 상태 변경 안내, 모달 사용 시 포커스 복귀, 모바일 확대를 포함한다. 현재 루트 viewport의 `maximumScale: 1`, `userScalable: false`는 확대를 제한하므로 반응형 적용 시 함께 재검토한다.
- 모바일 초안 기준은 360/768px, 데스크톱은 시안의 1440px에서 검증한다. 페이지 전체 가로 넘침을 숨겨 해결하지 않고 표에 한정된 스크롤·열 축소·모바일 상세 전환을 설계한다. 기존 CSS 색 토큰을 재사용하고 Figma의 Noto Sans KR와 현재 Geist의 한글 렌더링 차이도 확인한다. 폰트 추가는 실제 필요성을 확인한 뒤 결정한다.

## 13. migration·테스트 누락 보완

- migration은 실제 적용된 최종 버전을 확인한 다음 새 버전을 정한다. 현재 V1이 있다는 이유만으로 운영의 다음 버전을 확정하지 않는다. 초기 전개는 nullable 선택 컬럼과 빈 배열을 사용하고 기존 조회·legacy 요청이 동작하는 순서를 검증한다. 새 필드가 필수인 Entity를 스키마보다 먼저 배포하면 validate가 실패할 수 있다.
- FK는 `catalogFileId`에 맞는 조회·삭제 성능을 확인하고 참조 측 인덱스를 검토한다. 문의 상품 ID/FK·스냅샷은 추가하지 않는다. 상세 규격 JSONB의 표시·수정만을 위해 GIN 인덱스를 추가하지 않는다. PDF 참조·페이지 조합과 빈 배열 기본값이 JPA mapping과 일치하는지 확인한다. 처리 상태의 CHECK·기존 행 초기화 검증은 해당 기능을 채택하는 후속 작업이다.
- DB 검증 근거: PostgreSQL의 CHECK는 null을 허용할 수 있으므로 NOT NULL 및 쌍 필드의 null 조건을 별도로 설계한다. 다른 테이블의 PDF 페이지 수와 비교하는 규칙은 단순 CHECK로 구현하지 않고 서비스에서 문서 metadata를 검증한다. [PostgreSQL 제약 문서](https://www.postgresql.org/docs/current/ddl-constraints.html). 상세 규격은 객체 키 순서에 의존하지 않는 배열로 표현한다. [PostgreSQL JSON 문서](https://www.postgresql.org/docs/current/datatype-json.html).
- DDL 잠금·실행 시간은 대표 크기의 격리 DB에서 확인하고 대상별 lock/statement timeout과 실패 시 중단 기준을 정한다. 운영 전행 backfill을 무조건 한 transaction으로 실행하지 않는다. additive migration 후 애플리케이션을 되돌리는 경우 새 컬럼·업로드를 즉시 삭제하지 않는 복구 방안을 우선한다.
- 기존 `FlywayBaselineIntegrationTest`는 현재 버전이 문자열 `1`이라고 단정한다. 신규 migration을 추가하면 이 assertion도 새 migration 검증에 맞게 바꿔야 한다. 기존 스키마 fixture를 migrate한 뒤 데이터·참조·기본값이 보존되는 테스트를 추가한다.
- 해당 Testcontainers 테스트에는 `disabledWithoutDocker=true`가 있다. `gradlew test` 성공만으로 실제 PostgreSQL 검증 통과라고 보고하지 않는다. 실행/skip 결과를 구분하고 migration 변경의 완료 조건에는 실제 컨테이너 실행 성공을 포함한다.
- 프론트 package.json에는 현재 테스트 실행 script가 없다. lint/build는 상호작용 검증을 대신하지 않는다. 기존 도구로 가능한 순수 필터/선택 로직의 작은 검증과 명시된 수동 브라우저 시나리오를 사용하고, 새 테스트 프레임워크 도입은 필요할 때만 결정한다.

## 14. 검토 근거와 남은 결정

재검토한 소유 소스: `Product.java`, `ProductService.java`, `ProductRepository.java`, Product DTO, `InquiryService.java`, `InquiryPersistenceService.java`, Inquiry DTO, `CategoryService.java`, `SecurityConfig.java`, `UploadController.java`, `CloudinaryUploadService.java`, `V1__baseline_schema.sql`, `FlywayBaselineIntegrationTest.java`, 프론트 root/admin layout, 상품 폼/훅/목록, API client·types·products·inquiries·auth, `PARTNERS`, 검색어 변환, cache revalidation, package/build 설정.

후속 구현의 문서 갱신 대상에는 `docs/api-contract.md`뿐 아니라 `backend/docs/product-spec.md`, `backend/docs/inquiry-spec.md`, `docs/e2e-verification-spec.md`와 관련 도메인 작업 지침도 포함한다. 현재 문의 작업 지침은 읽음 변경 API를 기존 범위에서 제외하므로 신규 기능을 구현할 때 새 계약과 모순되지 않게 함께 갱신한다.

PDF의 배포 변경은 `docker-compose*.yml`·Nginx·Spring 업로드 설정·SecurityConfig와 `docs/deployment-spec.md`·`deploy/README.md`를 함께 갱신한다. 현재 저장소 배포는 Cloudflare Tunnel이며 오래된 문서의 직접 TLS 설명을 실제 경로로 오인하지 않는다. 원격 서버 설정은 이번에 확인하지 않았다.

브랜드 관계·상품 필수 입력·PDF 서버 저장/최대 1GB/공개/공유/상품별 페이지·자동 읽음·일반 문의·스냅샷 확장 제외는 0절대로 확정했다. 남은 설계는 **PDF 볼륨 경로·분할 API/검증 자원 한도·백업 설정, 신규 입력 제한 수치, 비교 상한과 반응형 동작**이다. 처리 상태·메일 오류 조사는 후속 작업이다. 확정 범위부터 API 계약과 구현안을 구체화할 수 있으며 이 문서 갱신에서는 SQL·애플리케이션 코드·운영 설정을 수정하거나 실행하지 않았다.

## 15. 목록 URL·검색·집계의 구체 동작안

아래는 3·12절의 미결정을 줄이기 위한 **권장 기본안**이다. 현재 지원 중인 URL 계약으로 간주하지 않는다.

| 상태 | URL 후보와 기본값 | 반영 시점·복원 규칙 |
|---|---|---|
| 검색어 | `q`, 기본 빈 문자열 | 엔터/검색 버튼에서 반영. 공백을 정리하되 화면에는 사용자가 입력한 언어를 유지한다. |
| 브랜드 | `companyId`, 생략하면 전체 | 기존 회사별 카테고리 관계를 사용한다. 독립 `brandId`는 도입하지 않는다. |
| 제품군 | `categoryId`, 생략하면 전체 | 이름 대신 ID. `/products/category/{id}` 진입은 해당 제품군을 고정 범위로 삼는다. |
| 등록 규격 | `spec`, 기본 빈 문자열 | 상세 규격 JSON이 아닌 요약 문자열의 부분 일치. 필터 적용 전 입력은 URL에 쓰지 않는다. |
| 정렬 | `sort`, 기본 `latest` | 후보는 `latest`, `nameAsc`, `nameDesc`. 최신순은 생성 시각 내림차순, 동률은 ID 내림차순으로 정의한다. 이름순의 언어 비교 기준은 한 곳에서 통일한다. |
| 페이지 | `page`, 기본 1 | 필터·검색·정렬 적용 시 1로 이동. 결과가 줄면 마지막 유효 페이지로 보정하고 0건은 페이지 1·페이지 버튼 없음으로 표시한다. |

- 적용된 상태는 URL을 기준으로 화면에 복원한다. 상세에서 브라우저 뒤로 가기, 새로고침, 주소 직접 접근에서 동일 결과·정렬·페이지가 보인다. 비교 선택과 적용 전 필터 초안은 URL에 저장하지 않는다. 입력할 때마다 브라우저 이력을 추가하지 않고 실제 적용·페이지 이동을 이력 단위로 삼는다.
- 초기화 기본안은 브랜드·규격 조건을 해제하고 페이지를 1로 돌리는 것이다. 검색어·정렬·현재 카테고리 범위와 비교 선택은 유지한다. 검색어 지우기와 전체 제품 복귀는 별도 조작으로 제공한다. 다른 초기화 범위를 채택하면 버튼 문구와 이 표를 함께 바꾼다.
- 양의 정수가 아닌 ID/page, 미지원 sort, 중복 query key의 처리 규칙을 고정한다. 권장안은 유효하지 않은 query 값을 기본값으로 보정하고 조건 해제 사실을 안내하는 것이다. 정상 형식이지만 존재하지 않는 카테고리의 전용 경로는 기존대로 404다. 전용 카테고리 경로와 query가 충돌하면 경로 ID가 우선한다.
- 처리 순서는 공개 제품 → 검색 → 브랜드 → 제품군 → 규격 → 정렬 → 페이지 분할이다. 결과 개수는 페이지 분할 전 개수다. 카테고리별 개수는 검색·브랜드·규격을 적용하되 현재 선택한 카테고리 조건과 페이지는 제외해 계산하는 안을 권장한다. 비교표는 페이지에 보이는 행만으로 다시 만들지 않는다.
- 현재 자동완성은 변환된 검색어 하나만 백엔드 이름 검색에 보낸다. 전체 목록만 모델명·용도 검색을 지원하면 같은 입력의 자동완성과 결과 화면이 달라진다. 전체 적용 시 두 검색의 대상 필드를 함께 확장하거나 자동완성의 제한 범위를 명시한다. 원문·변환 별칭으로 여러 요청을 사용한다면 ID로 중복 제거하고 원문 검색의 실패를 '0건'으로 숨기지 않는다.
- 검색 결과 query와 정렬·페이지 조합을 sitemap에 추가하지 않는다. canonical·index/noindex 정책은 `app/products/layout.tsx`와 각 페이지 metadata에서 확인하고, 필터 UI 추가로 무제한 URL 조합이 색인 대상이 되지 않게 결정한다.

## 16. 비동기 작업·입력 보존·오류 복구

- **업로드 응답의 대상 보존:** 현재 `useProductAdmin.handleImageUpload`는 완료 시 현재 폼에 URL을 넣는다. 상품 A 업로드 도중 취소하거나 상품 B 수정으로 전환한 뒤 A의 응답이 도착하면 B에 적용될 수 있다. 이미지/PDF 업로드 중 전환을 막거나 편집 대상·요청 식별자를 검사해 이전 응답을 무시한다. 요청 취소만으로 원격 파일이 삭제되었다고 판단하지 않는다.
- **종속 옵션 조회:** 회사/카테고리를 빠르게 바꾼 뒤 이전 조회가 늦게 끝나도 현재 옵션·선택값을 덮어쓰지 않는다. 재조회 실패는 '등록된 카테고리 없음'과 구분한다. 저장 시 선택 카테고리가 현재 폼의 유효한 옵션인지 확인하고 서버도 실제 존재와 채택한 브랜드 관계를 검증한다.
- **문의 상품 변경:** 상품 ID는 공개 화면의 현재 선택·복귀 링크에만 사용하고 제출은 기존 상품명 계약을 유지한다. 제품 재선택 시 이름·연락처·본문·동의 상태는 유지한다. 일반 문의로 바꾸면 선택 상품명·요약·복귀 링크만 비운다. 목록의 정상 0건·로딩 중·실패를 구분하고 실패해도 일반 문의를 접수할 수 있게 한다.
- **성공 후 화면:** 문의 접수 성공은 폼 오류 표시와 입력을 초기화하고 접수 완료 상태를 남긴다. 재접수 버튼을 누르기 전에는 같은 내용이 자동 전송되지 않는다. 관리자 저장 성공은 서버 응답을 목록에 반영한 후 편집을 종료하고 해당 행 또는 목록 제목으로 포커스를 돌린다. 실패 시 폼과 기존 업로드 연결을 보존한다.
- **실패 경계:** 최초 목록 로딩 실패는 오류와 재시도를, 정상 0건은 빈 상태를 표시한다. 재조회 실패 시 이미 표시 중인 목록은 남기되 갱신 실패를 알린다. 잘못된 입력은 필드 가까이에 표시하고 첫 오류로 포커스를 이동한다. 401 재로그인 시 자동 저장·자동 재전송하지 않으며, 입력을 보존한다면 현재 메모리 범위로 제한한다.
- **문의 읽음 응답:** 문의 A를 연 뒤 B를 선택했을 때 A의 늦은 읽음 응답이 B의 상세 선택이나 본문을 바꾸지 않는다. 응답의 문의 ID로 해당 행의 읽음만 갱신하고 서버도 다른 필드를 변경하지 않는다. 처리 상태 동시 변경 설계는 해당 기능을 채택하는 후속 작업에서 다룬다.
- **파일·텍스트 경계값:** PDF 파일당 최대 1GB는 확정했다. 조각 크기·분할 API·페이지 검증 자원 한도와 신규 필드의 최대 길이·규격 행 수·중복 항목명 정책은 구현 전에 계약에 기록한다. 프론트 제한과 서버 검증을 맞추고 한도 초과를 조용히 자르지 않는다. 파일 크기 오류는 multipart/프록시에서 거절되는 경우까지 확인한다. 이미지 없음뿐 아니라 원격 이미지 로드 실패도 대체 상태를 제공한다.
